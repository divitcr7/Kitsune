# Kitsune

An Android client with its own native UI over [miruro.cx](https://www.miruro.cx)'s catalog, with
episodes streamed from miruro.cx into the app's own native player. One Expo /
React Native app (TypeScript, `react-native-tvos`) ships as a single APK for Android phones and
Android TV; `tv/tizen` is a separate Samsung TV build (Preact, a TizenBrew module) on the same
miruro.cx catalog and streams, with its own `<video>` player.

## The rules about video

**Episodes play inside Kitsune, with no ads.** The app never opens a browser, and never loads a page
of miruro.cx's site (its pages carry ad networks). Video is played by `expo-video` (ExoPlayer) from
the HLS streams miruro.cx's API lists for an episode, or from a download on the device. Kitsune
never decrypts streams: an encrypted one (`#EXT-X-KEY`) is not downloaded.

miruro.cx sits behind Cloudflare, which turns away clients that aren't browsers and sometimes checks
a browser before letting it through. Kitsune's job is to **stay out of its way**:

- API calls go through a real browser: a hidden WebView on the site's origin (the bridge, below).
  Never call the API from native code, and never set a user agent, replay cookies or add headers to
  look like a browser.
- A Cloudflare check in the bridge is shown to the person (after a short grace period) and never
  answered for them. If it keeps coming back, say so on screen.
- Opening an `/api/` path as a page is blocked outright by the site's firewall (HTTP 403 "Sorry,
  you have been blocked"), so the bridge opens `/robots.txt` and calls the API from there.
- Stream and subtitle requests may carry only the `Referer`/`Origin` that the play API lists for
  that server, or go through miruro's own stream proxy (which needs no headers), as the site's
  player does.

## How playback works

1. `playEpisode` (`src/lib/nav.ts`) opens a session in `usePlayer`; `PlayerHost` renders `Player`.
   Show ids are miruro's; episode ids are `${showId}:${number}` (miruro's episodes have no ids).
2. `resolveEpisode` (`lib/miruro/resolve.ts`): the show's episode list (skip times),
   `/api/v1/anime/<id>/episodes/<n>/play`, `/api/config` and `/env2.js`. Shows are miruro's
   already, so nothing needs matching.
3. `candidates` (`streams.ts`) ranks streams: miruro's `providerOrder` (visible providers only), the
   provider's `variantOrder` within the sub/dub preference (`ssub` = clean video + subtitle files,
   `sub` = burned in), proxy URL first where the provider is proxied, then the stream direct with its
   listed headers. The last server that worked for a show goes first.
4. `Player` probes the first four playlists in parallel, then hands streams to the player one at a
   time; a stream that errors or isn't ready in 12 s gives way to the next. A mid-episode error
   retries the same stream once from where it was.
5. While playing: subtitle files are fetched and drawn as an overlay, `skip_times` give the skip
   pill, progress is saved every 5 s, and the end of an episode moves on to the next.

### The catalog

`lib/catalog.ts` maps miruro's catalog into the shapes the screens use, so the UI didn't change:
home rails (trending now, the season's list, coming soon, top movies, all-time), search and genres
(cursor paging; `enc()` escapes `! ' ( ) * ~` because the bridge only passes plain characters),
one schedule request (a week back and ahead) for New Episodes, the Schedule tab and alerts, show
details and episodes (specials numbered 20001+ and episodes not aired yet are left out).

### Data saved before 1.3

Store v4 / downloads v2 moved anime.nexus ids onto miruro's (`lib/migrate.ts`, pure, tested):
shows played before had a `links` entry and move exactly with their progress; the rest sit in
`pending` and `migrateRun.ts` finds them by exact title on miruro, five a launch; what it can't is
listed in My Stuff ("From the old catalog"). Downloads keep their folder (`dir`); unmovable ones
are `legacy` (they play offline but don't write history). Raw backups: `kitsune-store-v3-backup`,
`kitsune-downloads-v1-backup`.

The miruro catalog only answers the exact query shapes its site sends ("Unsupported catalog
request" otherwise; e.g. `limit=100` works for the AniList lookup and 50 doesn't). Keep the paths in
`lib/miruro/api.ts` as they are, and check a new one in a browser on the site first.

Responses with `application/octet-stream` are the gzipped JSON XORed with `miruro/catalog`. The
stream proxy URL is `PROXY + b64url(xor(url, key)) + ("~" + b64url(xor(referer, key)) if the server
lists a Referer) + "/pl.m3u8"` (`/sub.vtt` for subtitles), with `PROXY` and the hex `key` from
`/env2.js`. The second part is the Referer **value only**, not JSON of the headers (that form gets
HTTP 500). `scripts/check-miruro.mjs` pins both with vectors built by the site's own scheme.

Subtitles: never trust the API's `format`. icarus serves ASS files labelled "vtt" behind `.jpeg`
URLs, which answer only with the listed `Origin`/`Referer` (403 without, 500 through the proxy).
Proxied providers' subtitles come through the proxy's `/sub.vtt` as the site does.

### Player settings

Quality: `player.maxResolution` caps it, and for a real lock the candidate's master (through the
proxy, so its links need no headers) is copied to the cache keeping one variant (`hls.pinnedMaster`)
and played from `file://`. ExoPlayer drops custom headers for a `file://` source, so only proxied
links work inside one. Audio language uses `player.audioTrack` (icarus carries up to 14). Volume
boost and Anime4K upscaling need native code expo-video doesn't expose; they aren't offered.

### Downloads

`engine.ts` downloads one episode at a time, 3 segments in parallel, into
`<documents>/downloads/<id>/` (layout in `files.ts`): `plan.json` first (candidate, every segment
URL), segments as `.part` then renamed, subtitle cues as JSON, local playlists, and `master.m3u8`
last, whose presence marks it complete. It resumes from the first missing segment; expired links
(403/404/410, or segments that keep failing) are looked up again; space is checked as it goes. The
player plays a finished download from `file://` with no network. miruro's check is shown for a
download only when the person just tapped it (`asking`).

Downloads keep going in the background through `modules/kitsune-downloads` (a local Expo module):
`KitsuneDownloadService` is a foreground service (type dataSync, progress notification, Wi-Fi
lock) that runs the Headless JS task registered in `src/lib/downloads/background.ts` for as long as
the queue has work. That matters because React Native stops JavaScript timers in a backgrounded app
unless a Headless JS task is running (`JavaTimerManager`), and the engine depends on them. While a
download runs, the engine also makes the next episode's plan (`planAhead`), because Android
destroys the miruro bridge WebView when Kitsune is swiped away. Android 15 caps dataSync services
at a few hours a day (`onTimeout` stops it); a killed process resumes on the next launch.

### Notifications

`src/lib/notify.ts` (expo-notifications): miruro only answers a browser and the bridge tab exists
only while Kitsune runs, so nothing checks in the background. Whenever Kitsune opens (and on
resume, 15 minutes apart) it reads miruro's schedule (a week back, a week ahead) for shows in My
List or watched in the last 45 days: episodes out since last time notify now, and the coming
week's are scheduled as date-triggered notifications at their release time (`ep-<id>-<n>`, up to
50, the rest cancelled). The first sighting of a show is only noted. Also a "downloaded"
notification while Kitsune is in the background; a tap opens the show (or Downloads). The 1.2
background task is unregistered (and kept defined as a no-op). `index.js` is the app entry.

### The bridge

`MiruroBridge` mounts a WebView on `https://www.miruro.cx/robots.txt` the first time anything asks
the API, with `bridgeScript` injected at every load milestone (it is idempotent). The script goes
through the **gate** (below), posts `{ type: 'bridge' }`, and then answers
`window.__kitsuneApi(id, path)` (only `/api/...` and `/env2.js`) with a same-origin XHR, posting
`{ type: 'res', id, status, ctype, b64 }`. Decoding happens in the app. An HTML 403 from an API call
means Cloudflare wants another look: the tab reloads (so a check can show) and the call is sent
once more.

### The gate

`inject.ts` wraps every page script in `gate(run)`. It reads the document's HTTP status from
`performance.getEntriesByType('navigation')[0].responseStatus`:

- status < 400 (or unknown, on old engines): report `none` and `run()` immediately.
- status >= 400: wait for the DOM. A Cloudflare check (`window._cf_chl_opt`, its challenge
  elements, or its title) reports `check` and never calls `run()` on that document. Anything else
  reports `refused` with a short summary and then runs.

Recognise the check by `_cf_chl_opt` first. Its title is translated by language, and normal site
pages also contain a Turnstile box and Cloudflare's `/cdn-cgi/challenge-platform/scripts/jsd/`
script, so neither of those identifies a check page.

## Rules for `src/lib/inject.ts`

The scripts are JavaScript inside TypeScript template literals, so the compiler cannot see them.

- **ES5 only**: `var`, `function`, no arrow functions, no `let`/`const`, no template literals. They
  run in whatever WebView an old Android TV box has.
- Backslashes are doubled (`\\/api\\/`); one lost backslash breaks the whole script silently.
- Every `function name(` in one script must be unique (declarations hoist and overwrite).
- Scripts must be idempotent and work whether they land at document start or after load.
- End injected snippets with `true;`.
- `npm run typecheck` runs `scripts/check-player-script.mjs`, which parses every script and checks
  the rules above. Run it after any edit here.

## Phones and TVs

`isTV` (`src/lib/tv.ts`) switches layouts in the same components. On TV there is no touch: anything
the person must act on needs focus (`hasTVPreferredFocus`, `FocusBlock`, `web.requestFocus()`), and
sizes go through `tv(n)`. A TV has no browser and no Back button on screen; do not add either.

The Samsung module runs on `https://www.miruro.cx/robots.txt` itself (TizenBrew's `websiteURL`), so
it calls the API with same-origin XHR (`tv/tizen/src/miruro.ts`, decoded by `codec.ts`) and plays
in its own `<video>`: hls.js 1.5.20 from jsDelivr (quality and audio choices), native HLS where
hls.js can't run. A browser can't send a server's `Referer`, so the TV plays proxied streams only
(`tvCandidates`); icarus comes burned-in, and clean streams get the proxy's `/sub.vtt` drawn as an
overlay. An HTML 403 from the API reloads the page so Cloudflare's check shows (`shell.ts` steps
aside for it). Its output must be ES5 (`npm run build:tizen` fails otherwise; runtime gaps such as
`trimStart` go in `polyfills.ts`) and its CSS avoids flex `gap`, grid and custom properties. Test it
by running `dist/kitsune.js` in a desktop Chrome tab on that robots.txt page.

## Commands

```sh
npm ci
npm run typecheck     # tsc (app + tv/tizen) and the injected-script check
npm run lint
npm run build:tizen   # tv/tizen/dist/kitsune.js
npm run build:apk     # needs JAVA_HOME and ANDROID_HOME; dist/Kitsune-v<version>.apk
```

CI (`.github/workflows/ci.yml`) runs typecheck, lint and the Tizen build. There is no unit test
runner.

`.github/workflows/test-build.yml` builds an APK on every push to a `claude/**` branch (or when run
by hand) and publishes it as a release that is not marked latest. It is a separate app, "Kitsune
Test" (`app.kitsune.anime.test`, debug-signed, since CI has no release key), so it installs next to
the released Kitsune instead of replacing it. The in-app updater reads only the latest release and
only an APK named `Kitsune-vX.Y.Z.apk`, so it never offers these.

## Testing a player change

The app itself only runs on a device. Without one:

- `npm run typecheck` runs `check-miruro.mjs`: decoding a real captured response, the proxy URL
  scheme against one built by the site, show matching, stream ranking, VTT/SRT parsing.
- The TV module can be run as it is in a browser tab on that page (see tv/tizen/README.md).
- The bridge script can be run as it is in a browser tab on `https://www.miruro.cx/robots.txt`:
  define `window.ReactNativeWebView.postMessage`, eval `bridgeScript`, call `window.__kitsuneApi`,
  and check the `res` messages (status 200, `application/octet-stream` for catalog paths).

What only a device can show: ExoPlayer actually playing the proxied and direct streams, whether
Cloudflare lets the Android WebView through, and focus on Android TV. Say plainly in the write-up
what was and was not run on a real phone or TV.

## Conventions

- Comments say why, in a sentence, where the code alone would not. UI copy is plain and specific,
  with typographic apostrophes (`’`), and names miruro.cx or anime.nexus when a site is the cause.
- State lives in two zustand stores (`player.ts` in memory, `store.ts` persisted). Bump the persist
  `version` and add a `migrate` when a persisted field is removed or reshaped.
- A release is one commit titled `Kitsune vX.Y.Z: <what changed>` that bumps `version` in
  `app.json` and `package.json` and `versionCode` in `app.json`. Installed apps offer the update
  from the GitHub release; the APK must be signed with the release key, which is not in the repo.
- Keep `README.md` troubleshooting in step with what the screens actually say.
